# 硬件 PRD 智能拆解 Skill

## 一、这个 Skill 是做什么的

把一份硬件产品 PRD，一次性拆解成**五个专家工程角色** 的任务清单，颗粒度做到"工程师看完知道下一步做什么"，作为硬件研发工作流的**入口 Skill** ，下游可无缝衔接项目排期、BOM 整理、模具寻源等 Skill。

**五个角色的严格分工（不可合并、不可跨界）** ：

| 角色 | 负责领域 |
|---|---|
| 硬件工程师 | 主控、传感器、交互器件（按键/LED/扬声器）、电源、通信、存储 |
| 结构工程师 | **结构堆叠、装配、公差、防水、材质选型、模具约束** （不含 ID 造型与 CMF 设计本身；仅材质由结构提要求） |
| 工艺工程师 | SMT、组装工艺、密封、产测工装 |
| 品质管理工程师 | 可靠性测试、关键指标验证、来料检验、合规验证 |
| 成本分析工程师 | BOM 成本估算、关键物料询价清单、模具评估 |

说明：本表描述**角色边界** ；下方 Step 3 的映射表描述**分派规则** （PRD 关键词 → 角色），两者角度不同。

## 二、🔒 隐私与数据安全声明（重要）

硬件 PRD 通常包含**未公开的技术方案、BOM 成本、供应商名单、里程碑节奏** 等敏感商业信息。使用本 Skill 前请务必了解：

1. **数据处理路径** ：用户上传的 PRD 内容会被大模型读取并用于生成拆解报告；生成的报告默认会引用 PRD 原文若干处（用于追溯依据）。

2. **本 Skill 不会主动存储或外发** ：Skill 本身只是指令集，不会主动上传数据到任何第三方。

3. **风险位于对话上下文** ：真正的敏感数据流转发生在"用户 ↔ 大模型 ↔ 报告文件"这条链路上，需要用户根据自己所在的部署环境（公有云 / 私有化）自行评估。

4. **本 Skill 提供两种输出模式** ：完整模式（保留 PRD 原文引用）与脱敏模式（隐去型号、供应商、数字等敏感字段），由用户在每次执行前选择。

## 三、六大核心执行原则（每次执行必须遵守）

1. **忠实于 PRD** ：只做拆解和分派，不做设计决策，不臆造 PRD 中没有的规格。

2. **保留原文引用** ：关键规格用 `> 引用` 或行内引号引用 PRD 原文，便于追溯，全文至少 5 处原文引用（**脱敏模式下引用内容按规则替换** ）。

3. **保留不确定性** ：PRD 中标注"待确认""待定""TBD"的项目**原样保留** ，不替用户拍板。

4. **优先级严格遵守** ：完全遵循 PRD 原文的 P0/P1/P2 分级，不擅自调整。

5. **专业分工清晰** ：每个任务只归属**最相关的一个角色** ，不重复分派；跨领域任务在"协作说明"里注明。

6. **产出可执行** ：颗粒度清晰到"工程师看完知道下一步做什么"，避免"设计XX""考虑XX"这类空话。

## 四、边界说明（明确不做什么）

- ❌ 不适用于纯软件/纯 App/纯 Web 需求文档（识别到无硬件规格章节时应主动提示）

- ❌ 不做具体设计决策（例如不推荐具体芯片型号，除非 PRD 已指定）

- ❌ 不做深度可行性评估（不判断"14 天续航能否达成"，只列出"需验证 14 天续航"任务）

- ❌ 不修改、不质疑 PRD 内容（PRD 说双芯就双芯，不建议改单芯）

## 五、执行步骤（严格按顺序）

### 🔴 Step 0：数据敏感度确认（每次执行前必做，不可跳过）

无论用户如何触发本 Skill，**首次响应必须先输出以下提醒并等待用户选择** ，收到明确回复前不要开始拆解：

```
🔒 数据敏感度提醒

您即将拆解的 PRD 可能包含以下敏感信息：
- 未公开的主控/传感器型号、供应商名单
- BOM 成本、目标售价、模具费等商业数据
- 项目里程碑、内部代号、待确认商业决策

请选择输出模式：
 ①【完整模式】保留 PRD 原文引用（技术追溯性强，适合内部使用）
 ②【脱敏模式】隐去型号/供应商/数字/内部代号（适合跨团队分享、外部咨询、示例演示）
 ③【取消】不做拆解

请回复 1、2 或 3。
```
- 用户回复 `1` / "完整" / "内部用" → 进入 **Step 1 完整模式**

- 用户回复 `2` / "脱敏" / "保密" → 进入 **Step 1 脱敏模式** （加载 `references/desensitization_rules.md`）

- 用户回复 `3` / "取消" / "不做了" → 礼貌结束，不做任何处理

- 如果用户在初次触发时已经明确说"脱敏拆解""保密拆解""帮我脱敏一下" → 可**跳过询问** 直接进入脱敏模式，但要在报告开头注明"已按用户明示进入脱敏模式"

- 如果用户在初次触发时已经明确说"完整拆解""不用脱敏""内部资料没关系" → 可跳过询问直接进入完整模式

### Step 1：读取并理解 PRD

- 完整阅读用户提供的 PRD 文件。

- 提取以下要素形成"PRD 摘要卡"（内部用）：

    - 产品名称、版本号、文档日期

    - 一句话定位、目标用户、核心场景

    - 非目标声明（如"不替代医疗器械"）

    - 硬件规格表（主控/传感器/电源/通信/存储/结构/材质/防水/认证等）

    - 优先级分布（P0/P1/P2 各多少项）

    - 所有 **待确认 / 待定 / TBD**  事项（这是关键，全局汇总时要用）

- （PRD 摘要卡仅用于 Skill 内部推理，不出现在最终报告中）

- **脱敏模式下** ：在摘要卡阶段就按 `references/desensitization_rules.md` 建立字段替换映射表。

### Step 2：识别 PRD 结构完整性

- 对照 `references/hardware_prd_structure.md` 检查 PRD 覆盖度。

- 如果关键章节缺失（如没有硬件规格章节），在报告开头**加一个警告块** ，但仍继续拆解已有内容。

### Step 2.5：ID 定稿状态检查（结构工程师任务分派的前置条件）

在开始结构工程师任务分派前，必须先判定 PRD 中的 ID（工业设计）定稿状态。ID 是结构工程师的**输入** ，不是产出。

**三种状态判定规则** ：

| 状态 | 判定依据 | 结构任务分派策略 |
|---|---|---|
| **A. ID 已完整定稿** | PRD 包含：ID 效果图 或 具体外观尺寸图 或 CMF 方案稿 | 按 ID 稿正常分派结构任务；报告中 §4.1 引用 ID 稿页码/图号 |
| **B. ID 完全缺失** | PRD 完全没有形态、尺寸、外观描述 | ⚠️ **在报告开头加红色警告块** ："ID 缺失，结构工程师工作受阻"；结构任务清单**仅列出"硬件堆叠可行性预研"类任务** （PCB/电池/天线的空间约束），其余任务全部标注"待 ID 定稿后启动" |
| **C. 部分 ID（形态方向描述，但无正式 ID 稿）** | PRD 有形态方向的文字描述（如"无屏""杯身接近普通水杯""智能音箱形态"），但**无效果图/尺寸图/CMF 稿** | ⚠️ **在报告开头加黄色警告块** ："ID 未正式定稿，仅有形态方向；结构可基于形态描述做预研，正式设计需 ID 稿"；结构任务分为两类：**可预研的** （材质选型、防水等级、内部堆叠原则）标为 P0；**依赖 ID 稿的** （尺寸公差、模具分型面）标为 P0-hold "待 ID 稿" |

**例外分支** ：如果用户在触发本 Skill 时明确说"顺便帮我做 ID 建议"或"结构工程师这次也负责 ID"，则跳过本步骤，按用户要求分派（但报告中必须注明"应用户要求，本次结构范围含 ID"）。

**判定后再进入 Step 3。**

### Step 3：按角色分派任务

- 加载 `references/output_template.md` 作为骨架。

- 按"角色分工映射规则"（见下表）把 PRD 每一项规格/需求归口到对应专家。

- **每个任务的写法必须包含** ：任务描述 + 优先级 + PRD 依据（原文引用或章节号）+ 交付物。

- **脱敏模式下** ：PRD 依据列的引用内容必须按替换映射表处理，不能直接抄原文。

**角色分工映射速查表** ：

| PRD 中提到 | 归口角色 |
|---|---|
| 主控/MCU/SoC/协处理器/芯片架构 | 硬件工程师 |
| IMU/霍尔/温度/传感器 | 硬件工程师 |
| 按键/LED/扬声器/麦克风 | 硬件工程师 |
| 电池/续航/充电方式/功耗 | 硬件工程师 |
| Wi-Fi/BLE/4G/通信协议 | 硬件工程师 |
| Flash/存储容量 | 硬件工程师 |
| 产品形态/尺寸/容量 | **由 PRD 中的 ID 稿提供** （结构工程师不设计，仅按 ID 做内部堆叠）；若 PRD 无 ID → 触发「ID 缺失警告」 |
| CMF / 颜色 / 表面处理 | **ID/CMF 设计师** （本 Skill 不覆盖此角色，作为外部输入）；结构工程师**不** 做颜色/表面处理决策 |
| 材质选型（如 SUS304 vs Tritan） | 结构工程师（因涉及结构强度、防水、成型工艺） |
| 内部堆叠 / 装配 / 公差 / 模具约束 | 结构工程师 |
| 装配方式 / 内部布局 | 结构工程师 |
| 防水等级/IPXX | 结构工程师（提要求）+ 工艺工程师（做密封）+ 品质工程师（做验证） |
| 模具评估 | 结构工程师（提结构约束：分型面、脱模、壁厚）+ 成本工程师（做费用估价） |
| SMT/贴片/焊接 | 工艺工程师 |
| 组装工序/治具 | 工艺工程师 |
| 密封/点胶/超声焊接 | 工艺工程师 |
| 产测/硬件自检/量产测试 | 工艺工程师 |
| BOM 成本/物料价格/成本目标 | 成本分析工程师 |
| 模具费/开模摊销/注塑成本 | 成本工程师（估价） + 结构工程师（提结构约束） |
| 可靠性/寿命/跌落/温湿度 | 品质管理工程师 |
| 关键指标验证（如识别准确率、续航实测） | 品质管理工程师 |
| 来料检验/IQC | 品质管理工程师 |
| 认证/合规/CCC/SRRC/GB4806/UN38.3 | 品质管理工程师 |

### Step 4：为每个专家模块补充"⚠️ 待确认项"小节

- 从 Step 1 提取的待确认清单中，把与该角色相关的项挑出来。

- 每项写明：待确认内容 + 影响 + 建议责任方（引用 PRD 原文的"责任方"字段，若有）。

### Step 5：写"下游协作建议"模块（雷打不动）

- 必须原样输出以下三个下游 Skill 建议（表格形式）：

| 优先级 | 建议 Skill | 输入来源 |
|---|---|---|
| 🥇 | 项目排期 Skill（已有） | 硬件工程师 + 结构工程师任务中的所有 P0/P1 项 |
| 🥈 | BOM 整理 Skill（待做） | 硬件工程师的选型清单 |
| 🥉 | 模具寻源比价 Skill（已有） | 结构工程师任务中的模具件 |

### Step 6：写"全局风险汇总"模块

- 把 PRD 里所有"待确认""风险""待定"事项汇总成一张表。

- 字段：风险/待确认项 | 影响 | 优先级 | 建议责任方 | 出处（PRD 章节号）。

- 如果 PRD 本身已有"风险与待确认"章节，直接以其为主，做归类和精简即可。

### Step 7：保存输出（双格式输出：md + xlsx）

本 Skill 采用双输出策略——同一份拆解结果同时生成两个文件，分别服务于**阅读评审** 和**任务执行** 两种场景。**两个文件都必须生成** ，不可只输出其一。

#### 7.1 Markdown 输出（供阅读、评审、存档）

- 文件名规则：

    - **完整模式** ：`{产品名}_PRD拆解_{YYYY-MM-DD}.md`

    - **脱敏模式** ：`{产品名}_PRD拆解_脱敏版_{YYYY-MM-DD}.md`

- 保存位置：当前工作区根目录

- 格式：UTF-8 编码的 Markdown

- 内容：完整 md 报告，含 ID 警告块、原文引用块、颜色标记、9 个主体部分

- **脱敏模式下** ：报告开头必须加一段声明："本报告已按脱敏规则处理，隐去具体型号/供应商/数字/内部代号，仅保留结构与流程演示价值。"

#### 7.2 Excel 输出（供任务执行、跟踪、导入项目管理工具）

- 文件名规则：与 md 同名，扩展名改为 `.xlsx`

- 保存位置：当前工作区根目录

- 结构：**7 个 Sheet** （0-总览 / 1-硬件 / 2-结构 / 3-工艺 / 4-品质 / 5-成本 / 6-全局风险）

- 详细规范：**必须加载 `references/excel_output_spec.md`**  作为生成依据，不可临时决定列结构或样式

- 关键要求：

    - 每张任务表 9 列（序号/子块/任务/优先级/阻塞条件/PRD 依据/交付物/负责人/计划日期/状态）

    - 后 3 列（H/I/J）留空供工程师填写

    - J 列（状态）加下拉验证：未开始 / 进行中 / 已完成 / 阻塞

    - **P0-hold 双重保险** ：优先级列黄色高亮 + 整行淡黄底色

    - 每张 Sheet 冻结首行，表头深蓝底色白字加粗

#### 7.3 交付说明

生成完毕后，Skill 应在回复末尾明确告知用户两个文件的路径，例如：

已完成拆解。共生成两份文件：

- 📄 {产品名}*PRD拆解*{YYYY-MM-DD}.md — 供阅读评审

- 📊 {产品名}*PRD拆解*{YYYY-MM-DD}.xlsx — 供任务分派与跟踪（含负责人/日期/状态空列）

### Step 8：自检

交付前逐项核对：

- 五个专家模块都有实质内容，不能有空模块

- 全文至少 5 处引用了 PRD 原文（用 `>` 或引号）

- 所有 PRD 中的"待确认"事项都在"全局风险汇总"里出现

- 每个专家模块都有"⚠️ 待确认项"小节

- "下游协作建议"表格完整（3 行都在）

- 9 个主体部分顺序正确（元信息 → 产品定义 → 硬件 → 结构 → 工艺 → 品质 → 成本 → 下游协作 → 全局风险）

- 没有做设计决策（未擅自推荐具体型号/方案）

- ID 定稿状态已判定（A/B/C 三选一），且结构工程师任务分派遵循了对应策略

- 结构工程师任务清单**不包含 ID 造型设计任务** （如"完成 ID 效果图""制作 CMF 方案书"）；这些任务归属 ID/CMF 设计师（外部角色）

- **同时生成 md 和 xlsx 两个文件** ，缺一不可

- xlsx 文件严格遵循 `references/excel_output_spec.md` 规范（7 个 Sheet、9 列结构、P0-hold 双重高亮、状态列下拉验证）

- **【脱敏模式专属】** ：全文无具体型号（如 ESP32-C6、BMI270）、无供应商名（如乐鑫、Bosch）、无绝对数字（mAh/ml/元），改为占位符

### 示例 A：用户默认触发

**用户输入** ：

"帮我拆解一下这个 PRD"（附一份硬件 PRD 文件）

**Skill 执行** ：

1. **先弹出 Step 0 数据敏感度确认** ，等待用户回复 1/2/3

2. 用户回复后进入对应模式

3. 按 Step 1\~8 执行

4. 输出："已完成拆解（模式：完整/脱敏），共分派 XX 项任务给 5 位专家，其中 P0 项 XX 个。文件已保存至：..."

**用户输入** ：

2. 在报告开头注明"已按用户明示进入脱敏模式"

3. 按 Step 1\~8 执行（Step 1/3/7 应用脱敏规则）

### 示例 C：用户明示完整

**用户输入** ：

"帮我完整拆解这个 PRD，内部用的不用脱敏"

1. 跳过 Step 0 询问，直接进入完整模式

2. 按 Step 1\~8 执行

## 八、常见问题

### Q1：PRD不完整（缺硬件规格章节）能用吗？

可以。skill会在报告开头加警告块提示缺失章节，但仍会拆解已有内容。不过缺关键章节会影响任务分派的完整性，建议先补齐PRD再拆解。如果PRD完全是软件需求文档（无任何硬件规格），skill会主动提示"本文档不适用本Skill"并终止。

### Q2：完整模式和脱敏模式的区别是什么？

完整模式保留PRD原文引用（型号、供应商、数字、内部代号），适合内部研发使用。脱敏模式将这些敏感信息替换为占位符（如"主控芯片A""供应商B""XX mAh"），适合跨团队分享、外部咨询、比赛报名、公网演示等场景。两种模式的任务分派逻辑完全一样，只是输出内容的敏感度不同。

### Q3：五个专家角色能合并吗？比如小团队没有专职工艺工程师？

不能合并。本skill的设计原则是"角色边界不可跨界"，每个任务只归属最相关的角色。小团队的情况，一个人可以身兼多角（比如硬件工程师兼工艺），但任务清单仍然按角色分开列。这样你清楚知道这个人需要在哪些角色间切换，也方便后续招人时明确岗位需求。

### Q4：skill会帮我做设计决策吗（比如推荐芯片型号）？

不会。本skill只做拆解和分派，不做设计决策。如果PRD已经指定了芯片型号，skill会忠实引用并分派给硬件工程师做选型验证。如果PRD没指定，skill只会列出"需选型主控芯片"这个任务，不会替你选。

### Q5：ID（工业设计）缺失会怎样？

skill会判定ID定稿状态（A已定稿/B完全缺失/C部分），并在报告开头加对应级别的警告。ID完全缺失时，结构工程师的任务仅列出"硬件堆叠可行性预研"类任务，其余标为"待ID定稿后启动"。这是因为结构工程师的输入是ID稿，没有ID就无法做正式的结构设计。

### Q6：输出的Excel能导入项目管理工具吗？

可以。Excel采用标准化的9列结构（序号/子块/任务/优先级/阻塞条件/PRD依据/交付物/负责人/计划日期/状态），兼容Jira、飞书项目、钉钉项目管理等工具的CSV导入格式。状态列内置下拉验证（未开始/进行中/已完成/阻塞），可直接在Excel中跟踪。

### Q7：能处理多大的PRD？

PRD篇幅无硬性限制，但超过50页时大模型可能遗漏细节。
